## 1. 심사 총칙
[근거: App Review Guidelines]
- App Market은 **운전자 주의 분산 요소**(운전자 안전을 위협하거나 위험한 행동을 유도하는지)와 **사이버보안 위협 요소**를 앱 심사에서 중점적으로 검증한다.
- 차량 운행 안전에 위험할 수 있다고 판단되면 어떤 경우든 거부될 수 있다.
- 가이드를 다 지켜도 위험 요소가 완전히 배제됐다는 뜻은 아니며, 추가 위험이 보이면 거부될 수 있다.
- 심사 영역 5개: 콘텐츠 안전성 / 기능·성능 안정성 / 운전자 주의 분산 최소화 / 등록정보 / 개인정보·보안.

## 2. 주행 중 동작 규정 (가장 중요)

### 2.1 DO 선언과 기본 동작
[근거: 지역별 주행 규제 정책]
- 주행 규제는 차량의 속도·기어·브레이크 신호와 지역별 안전 규정에 따라 적용된다.
- **DO를 선언하지 않은 앱**: Parking 중 사용 가능, Drive 중 **사용 불가**.
- DO를 선언한 앱도 주행 중에는 `CarUxRestrictions`의 `ActiveRestrictions`를 보고 기능별 제한을 직접 적용해야 한다. [근거: 주행 규제 개발 가이드]

### 2.2 주행 중 기능 제한 (Driving 상태)
[근거: 지역별 주행 규제 정책]

| 기능 | 플래그 | 북미 | 유럽 | 그 외 지역 |
|---|---|---|---|---|
| 키보드 | `NO_KEYBOARD(8)` | ⛔ | ✅ | ✅ |
| 다이얼패드 | `NO_DIALPAD(1)` | ⛔ | ✅ | ✅ |
| 통합 검색 | `NO_KEYBOARD`, `NO_FILTERING(2)` | 음성 한정 | ✅ | ✅ |
| 미디어 앱 로그인·설정·검색 | `NO_SETUP(64)` 외 | ⛔ | ⛔ | ✅ |
| 디지털키·도어·시트·차량 설정 | `NO_SETUP(64)` | ⛔ | ⛔ | ⛔ |
| 동영상 시청 | `NO_VIDEO(16)` | ⛔ | ⛔ | ⛔ |
| 내비게이션 검색 | `NO_KEYBOARD`, `NO_FILTERING` | ⛔ | ✅ | ✅ |
| QR 로그인 | `NO_SETUP(64)` | ⛔ | ⛔ | ⛔ |
| 매뉴얼(대용량 텍스트) | `LIMIT_CONTENT(32)`, `LIMIT_STRING_LENGTH(4)` | ⛔ | ⛔ | ⛔ |

- Parking 상태에서는 전부 사용 가능.
- 한국은 "그 외 지역"에 해당하는 것으로 보임(추정). 플랫폼 버전·양산 차량에 따라 다를 수 있다고 명시돼 있음.

### 2.3 주의 분산 방지 UX 원칙
[근거: 주행 안전을 고려한 설계, UI Design Guide 소개]
- 운전자는 1~2초 안에 정보를 파악해야 함 → 핵심 정보만 노출.
- 운전 중 동영상, 애니메이션 이미지, 텍스트 자동 스크롤로 시선을 끌면 안 됨.
- 한 손으로 조작 가능해야 하며, 운전자의 손발을 움직이도록 유도하면 안 됨.
- 자주 쓰는 기능은 첫 화면·상단에. 드롭다운·다단 메뉴 남용 금지.
- 큰 터치 영역, 높은 대비, 텍스트 최소화. 키보드 입력보다 프리셋·최근 항목·음성 입력 우선.
- 게임, 인터넷 서핑, 피트니스 등 주의를 분산시키는 활동을 유도하지 않음.

### 2.4 알림 관련 (⚠ 기존 4관문 문구 정정)
[근거: 운전자 주의 분산 요소 최소화 설계 > 미디어 앱 설계]
- 원문은 "미디어 앱은 헤드업 알림을 게시해서는 안 됩니다. 운전과 관련되지 않은 알림은 사용할 수 없습니다."이며, **미디어 앱(동영상·게임·브라우저) 항목 아래**에 있다.
- 모든 앱에 대한 일반 조항으로 단정하면 안 된다. 다만 개인정보·보안 가이드도 "반복적인 알람으로 불편을 야기하는 앱"은 제외될 수 있다고 적고 있어, 주행 중 알림을 자제하는 방향은 맞다.
- 미디어 앱은 주행이 시작되면 일시 중지하고 UI를 숨겨야 하며, 운전 중에는 일시 중지를 해제할 수 없어야 한다.

## 3. 퍼미션·API 사용
[근거: Overview > Vehicle SDK API 사용 및 앱 심사, 앱 기능 및 성능 안정성 > SDK·API 사용 심사, 앱 보안 가이드]
- Vehicle SDK API를 쓰려면 퍼미션을 선언해야 하고, 퍼미션은 **Pleos App Market과 사전 협의·승인된 범위**에서만 선언할 수 있다. 미승인 퍼미션을 선언하거나 해당 API를 호출하면 심사 불통과.
- API 지원 여부는 도메인별 `checkXXXCapabilities`로 먼저 확인.
- 차량 상태를 바꾸거나 운전 안전에 영향을 주는 SDK·API에는 별도 심사 기준이 적용된다.
- 공식 제공·허용된 API만 사용하고, 앱 기능과 직접 관련된 범위에서만 호출.
- 권한 최소화: 실제로 필요한 권한만 요청.

## 4. 개인정보·위치정보
[근거: 사용자 개인정보 및 보안, Pleos App Market 등록정보, 보안 및 개인정보 보호를 고려한 설계]
- 개인정보에는 다른 정보와 쉽게 결합해 개인을 알아볼 수 있는 정보도 포함된다.
- 수집 시 필수: 수집 항목·목적·보유기간·거부 권리 고지 + **명시적 동의 절차**.
- 동의 UI 요구사항:
  - 동의/거부 화면은 모호하지 않게.
  - **동의 버튼을 누르는 것 외의 동작**(뒤로 가기, 빈 공간 터치 등)을 동의로 간주하면 안 됨.
  - 허가받은 항목의 데이터에만 접근.
- 동의 철회 시 즉시 활용을 중단하고 저장된 데이터를 삭제해야 함.
- 아동 개인정보는 법정대리인 동의 필요.
- 개인정보를 처리하면 **개인정보처리방침**, 위치정보를 쓰면 **위치정보 이용약관**을 함께 제출.
- 차량은 여러 사람이 함께 쓰는 기기 → 운전자 교체 시 쉽게 로그아웃·계정 전환이 가능해야 함. 토큰은 Keystore 등 안전한 저장소에.
- 차량 밖으로 나가는 데이터: 차량 ID·사용자 ID 익명화/가명화 정책 수립, **운전 중 행동 데이터를 마케팅 목적으로 쓰지 않도록** 구분.

## 5. 보안 (앱 보안 가이드 요점)
[근거: 앱 보안 가이드 — "준수하지 않을 경우 앱 심사를 통과하지 못할 수 있습니다"]
- 기기에 저장하는 민감정보는 암호화(SharedPreferences, SQLite, 캐시 포함). 키는 Android Keystore, 소스·리소스 하드코딩 금지.
- 로그에 민감정보 기록 금지 → 출시 전 로그 비활성화 또는 마스킹.
- 토큰·비밀번호를 URL 경로·쿼리에 넣지 말 것(Authorization 헤더 사용).
- 외부 통신은 HTTPS, **TLS 1.2 이상**(1.3 권장).
- 외부에서 호출할 필요 없는 Activity·Service·Receiver·Provider는 `exported=false`.
- 민감정보를 암시적 브로드캐스트로 보내지 말 것.
- 배포 앱은 **정식 서명 인증서**, **디버깅·WebView 원격 디버깅 비활성화**.
- 서버 주소는 IP 고정보다 도메인으로.

## 6. 기능·성능·화면
[근거: 앱 기능 및 성능 안정성, 앱 구조 및 동작 모델, UI Design Guide 소개]
- 설치·실행·사용 중 오류(강제 종료, 화면 멈춤, 터치 미인식) 없어야 함.
- **테스트용 더미 데이터·임시 파일·임시 콘텐츠가 앱에 남아 있으면 안 됨.** 심사 앱 = 실제 서비스 앱.
- 응답 시간 기준:
  - 앱 실행 10초 이내, 콘텐츠 로드 10초 이내
  - 버튼 반응 2초 이내. 넘으면 로딩 중임을 UI로 표시
  - 터치 후 터치 효과까지 **0.25초 이내**
- 백그라운드에서 돌아오면 마지막 상태 복원(수 시간 이상 지나면 기본 상태 허용).
- 재부팅이나 핵심 기능과 무관한 시스템 설정 변경을 사용자에게 요구하면 안 됨.
- 화면:
  - Driving view(운전자 쪽 고정 영역)는 앱이 가리거나 종료할 수 없음.
  - 앱 영역은 최대 2개 window. 1개 window = portrait, 2개 확장 = landscape → **두 형태 모두 설계**.
  - 해상도·window 크기가 바뀌어도 상태 손실·레이아웃 깨짐 없이 같은 기능 유지(기능 패리티).
  - 레터박스 없이 디스플레이를 채울 것(한 방향 미세 레터박스만 허용), 호환성 모드 실행 금지.
- 백그라운드에서는 불필요한 상주·타이머·폴링·네트워크 요청 최소화.
- 앱 카테고리를 설계 시점부터 정해야 하며, 카테고리와 맞지 않는 기능이 있으면 거부될 수 있음.

[근거: 콘텐츠 안전성, Pleos App Market 등록정보]

## 8. 1순위(정산 앱)에 대한 검토 결과

### 그대로 강점이 되는 것
- **DO를 선언하지 않으면 주행 중에는 플랫폼이 앱 사용을 막는다.** "주차 후에만 동작"은 따로 만든 제약이 아니라 플랫폼 기본 정책과 일치하는 설계라고 기획서에 쓸 수 있다.
- 심사 중점(주의 분산)과 정면으로 맞는 구조라 4관문은 통과.

### 설계에 반영해야 하는 것
1. **주행 중 데이터 수집 방식**: 좌석 점유는 주행 중에 바뀔 수 있다(중간 승하차). UI 없이 백그라운드에서 리스너로 받는 것은 금지 조항이 없지만, 폴링·상주를 최소화하라는 규정이 있으므로 `register…` 리스너 방식으로 구현. 주행 중 화면 표시나 알림은 하지 않는다. (주행 중 백그라운드 수집이 허용되는지는 설명회에서 확인 권장 — 추정)
2. **개인정보**: 탑승자 이름·연락처·송금 계좌/링크를 다루면 개인정보 처리 대상. 동의 화면, 처리방침, 철회 시 삭제, Keystore 저장이 필요. 저장 정보를 최소화할수록 부담이 줄어든다.
3. **위치정보**: 경로·목적지·이동 거리를 정산 근거로 쓰면 위치정보 이용약관 대상.
4. **공유 기기 대응**: 차를 여러 사람이 쓰므로 운전자(정산 주체) 전환이 쉬워야 함.
5. **송금 연동**: 앱 안에서 직접 결제·송금을 처리하면 금융 정보 보안 부담이 커진다. 외부 송금 앱 링크나 QR 정도로 두는 쪽이 안전(추정).
6. **카테고리**: Lifestyle 또는 Mobility Services 중 선택해야 함. 정산은 "일상생활 관리"에 가까워 Lifestyle이 자연스러워 보임(추정).
7. **화면**: 정산 결과 화면을 portrait/landscape 두 형태로 설계. 터치 피드백 0.25초, 로딩 2초 넘으면 로딩 표시.
8. **제출 빌드**: release APK는 정식 서명 + `debuggable=false` + 테스트 더미 데이터 제거. 공모전 APK 제출 규칙과 함께 체크.
