# 백그라운드 동결 실험 결과 (PRD 5.4)

- 실험: 이민하 · 2026-10-30 · Pleos Connect Emulator v2.1.0(`Pleos_Connect_2_1_0`), Vehicle SDK 2.3.2, NaviHelper 3.0.5
- 질문: 경로 안내 등으로 앱이 뒤로 밀렸을 때 크루즈·브레이크·조향 이벤트를 계속 받을 수 있는가

## 결론

1. **원인은 Android 14의 캐시 앱 동결(cached app freezer)이다.** 앱이 화면에서 사라지고 약 10초 뒤 `isFrozen=true`가 되고, 그동안 코드가 전혀 돌지 않는다.
2. **언 동안의 이벤트는 사라지지 않지만, 앱이 다시 앞으로 올 때 한꺼번에 늦게 들어온다**(실험에서 13초 지연, 5개가 같은 밀리초에 도착). 해제 판정은 시각(해제 직전 2초 안 브레이크)과 그 순간의 위치가 필요하므로 **이 상태로는 쓸 수 없다**.
3. **포그라운드 서비스(시도 ①)로 해결된다.** 프로세스 상태가 `FGS`로 유지되어 얼지 않고, 뒤에 있는 동안 주입한 이벤트를 1초 안에 실시간으로 받았다. 5분 연속 백그라운드에서도 동일(아래 표).
4. **멀티 윈도우(시도 ②)는 불가.** 시스템에서 분할 화면이 꺼져 있다(`persist.sys.systemui.splitscreen.enabled=0`). Pleos 화면은 왼쪽 주행 뷰 + 오른쪽 앱 영역 하나로 고정이라 내비와 우리 앱을 나란히 둘 수 없다.

5. **시동(부팅) 때 자동으로 켜진다.** 첫 실행에서 동의한 뒤에는 앱을 열지 않아도 `BOOT_COMPLETED`로 서비스가 켜지고 신호를 실시간으로 받았다(재부팅 2회). 단 서비스가 뜬 직후 약 5초(SDK 연결 중)는 이벤트를 놓칠 수 있다.
6. **알림은 알림 센터에 카드 한 장으로만 보인다.** 상단 바 아이콘·팝업 없음(중요도 LOW). 시스템 서비스들의 "실행 중" 카드와 같은 목록에 있다.
7. **여러 상황에서 일관되게 유지된다.** 서비스 하나를 켠 채 다른 앱 3종·경로 안내·주행 D80·앱 화면 닫힘·시스템 메모리 회수(`am kill`)를 차례로 만들었는데, 프로세스가 한 번도 바뀌지 않았고 7개 상황 모두 51~84ms 안에 신호를 받았다.

→ **권장: 주행 기록은 포그라운드 서비스에서 돌리고, 부팅 수신기로 시동 때 자동 시작한다**(아래 "결정 사항"). 시연 범위를 "앱이 화면 앞에 있는 상태"로 줄일 필요는 없고, PRD 4절의 "앱은 따로 조작하지 않아도 백그라운드에서 동작" 시나리오도 에뮬레이터 기준으로는 가능하다(첫 실행 동의 이후).

## 결과 표

| 실행 | 수집 방식 | 앱을 뒤로 보낸 방법 | 뒤에 있는 동안 상태 | 뒤에서 주입한 5개 이벤트 |
|---|---|---|---|---|
| `a-probe-route` | 서비스 없음(현재 `CruiseBreakerApp`과 같은 구조) | 경로 안내 시작 → 내비가 앞으로 | `isFrozen=true`, tick 54초 끊김 | 앱이 앞으로 돌아온 순간 한꺼번에 도착(13초 지연) |
| `b-fgs-route` | 포그라운드 서비스 | 경로 안내 | `isFrozen=false`, `cur=FGS`, tick 끊김 없음 | 실시간(1초 안) |
| `b-fgs-route-5min` | 포그라운드 서비스 | 경로 안내, 5분 대기 | `isFrozen=false`, `cur=FGS`, tick 338개 끊김 없음 | 실시간(1초 안) |
| `probe-drive` / `fgs-drive` | 둘 다 | 기어 D + 80km/h | 앱이 그대로 앞에 있음 → 얼지 않음 | 실시간 |

- "뒤에서 주입": Virtual Console로 크루즈 `ready`(=ENABLED, 시연상 "해제"), 브레이크 50→0, 조향 30→0.
- 앱이 뒤로 간 지 약 9~10초 뒤 마지막 tick이 찍혔다 → 동결까지 유예 약 10초.

### 시동(부팅) 자동 시작 — `boot1`, `boot2`

첫 실행에서 동의 플래그를 저장(실제 앱에서는 S5 첫 실행 동의 시점)하고, `RECEIVE_BOOT_COMPLETED` 수신기가 동의한 경우에만 포그라운드 서비스를 켠다. `adb reboot` 뒤 앱은 한 번도 열지 않았다.

| 실행 | 부팅 완료까지 | 서비스 시작까지(부팅 완료 후) | 앱을 열지 않은 채 주입한 4개 이벤트 |
|---|---|---|---|
| `boot1` | 24초 | 17초 | 서비스 시작 직후(약 5초 안)에 주입 → 크루즈는 받았지만 `brake=true` 1개 놓침. SDK 연결 중이었음 |
| `boot2` | 21초 | 11초 | 20초 기다린 뒤 주입 → 4개 모두 순서대로 실시간 수신 |

- 부팅 완료 후 서비스까지 10~20초 걸리는 이유: 시스템 사용자(0)가 먼저 뜨고, 운전자 프로필(사용자 10)이 뒤에 시작되면서 그 사용자에게 `BOOT_COMPLETED`가 간다.
- 시동 직후 몇 초 동안은 놓칠 수 있다 → 크루즈는 보통 고속도로에서 켜므로 영향은 작지만, 판정 로직은 "연결 직후 첫 값"을 해제로 착각하지 않게 할 것.

### 알림 모양·위치

- 상단 바에 아이콘이 생기지 않고 팝업도 없다(채널 중요도 LOW).
- 알림 센터(위에서 끌어내림)를 열면 카드 한 장: 앱 아이콘 + "FreezeProbe 기록 중". 같은 목록에 "Pleos UI service", "Convenience mode manager" 같은 시스템 "실행 중" 카드가 있다 → 우리 카드가 튀지 않는다.
- 실제 앱에서는 제목을 "크루즈브레이커 주행 기록 중"처럼 바꾸고, 운전자가 끌 수 있게 할지(설정 S4)는 기획에서 정한다.

### 여러 상황에서 유지 — `d-situations`

서비스 하나를 켠 채 아래 상황을 차례로 만들고, 상황마다 15초(동결 유예 10초보다 길게) 기다린 뒤 브레이크 50→0을 주입했다. 주입 시각은 에뮬레이터 시계로 쟀다.

| 상황 | 동결 | 프로세스 | 브레이크 수신 지연 |
|---|---|---|---|
| 설정 앱을 앞으로 | 아니오 | 같은 pid | 53ms |
| 전화·메시지 앱 | 아니오 | 같은 pid | 65ms |
| 갤러리 앱 | 아니오 | 같은 pid | 51ms |
| 경로 안내 시작 | 아니오 | 같은 pid | 82ms |
| 경로 안내 + 기어 D·80km/h | 아니오 | 같은 pid | 77ms |
| 앱 화면을 뒤로 가기로 닫음(서비스만 남음) | 아니오 | 같은 pid | 84ms |
| 시스템 메모리 회수(`am kill`) | 아니오 | **같은 pid(죽지 않음)** | 66ms |

- 전체 약 2분 동안 tick 간격 최대 1.0초, 빈틈 0회.

## 함께 확인한 것

- **주행 중 DO 차단은 이번에 재현되지 않았다.** 크루즈브레이커 `app`(main, adb 설치)과 실험 앱 모두 기어 D·80km/h에서 화면이 그대로 떠 있었다(`topResumedActivity`가 우리 앱). 장호연 handoff의 "주행 중 차단" 관찰과 조건이 다를 수 있음(예: 주행 중에 앱을 새로 실행하는 경우) → 장호연과 조건 확인 필요.
- 조향 리스너는 값이 안 바뀌어도 약 3초마다 `-0.0`을 보낸다(잡음). 해제 감지에서 조향을 쓸 때 변화량으로 거를 것.
- `CruiseBreakerApp`은 지금 `Application.onCreate`에서 수집을 시작한다. 프로세스가 살아 있어도 서비스가 없으면 얼기 때문에, 이 구조만으로는 백그라운드 기록이 안 된다.

## 결정 사항 (이민하, 2026-10-30 — 이견은 장호연에게)

1. **서비스 타입은 `specialUse`.** 실험(부팅 자동 시작 포함)에서 동작을 확인했다. `location`은 위치 런타임 권한이 필요하고 부팅(백그라운드) 시작과 충돌할 위험이 있으며, 위치는 어차피 NaviHelper로 받는다. 주최 측이 다른 타입을 요구하면 바꾼다.
2. **구현은 이민하**가 `feat/recording-service` PR로 올린다(리뷰 Claude, 머지 장호연).
3. **자동 기록은 S5 동의 후 기본 켜짐, S4에서 끌 수 있다.**
4. **S5 동의 화면에 자동 기록 안내를 넣는다**: "시동을 걸면 앱을 열지 않아도 주행을 자동으로 기록합니다".
5. **PRD 4절 "따로 조작하지 않아도 동작"에 "첫 실행 동의 이후"를 붙인다.**

## 아직 확인 못 한 것

- **실차의 시동 방식**: 에뮬레이터는 완전 재부팅으로만 시험했다. 실차가 시동 off 때 완전히 꺼지지 않고 절전(suspend)했다가 깨어나는 방식이면 `BOOT_COMPLETED`가 오지 않는다. 대신 프로세스가 살아 있던 채로 깨어날 가능성이 높지만 확인 불가 → 주최 측 문의 후보
- 수십 분 이상 장시간 주행, 앱마켓 심사에서 FGS·부팅 자동 시작 허용 여부
- 사용자가 알림 센터에서 카드를 밀어 지우거나 앱 설정에서 강제 종료했을 때(실험하지 않음)
- 동결 중 이벤트가 아주 많이 쌓일 때(바인더 버퍼 초과) 유실·강제 종료 여부 — 서비스를 쓰면 동결 자체가 없어 해당 없음

## 재현 방법

실험 앱은 저장소 밖 로컬 폴더에 있다(팀 규칙상 담당 경로가 아니라 커밋하지 않음): `hyundaiapp/experiments/freeze-probe/`

```bash
cd experiments/freeze-probe && ./gradlew assembleDebug && adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell pm grant --user 10 com.hyundaiapp.freezeprobe android.permission.POST_NOTIFICATIONS
bash run.sh <이름> <probe|fgs> <route|drive|home>   # 1회 약 90초(WAIT=초 로 대기 시간 조절)
bash analyze.sh <이름>                               # PC 주입 시각과 앱 로그를 합쳐 보여 주고 tick 빈틈(동결)을 표시
SETTLE=20 bash boot-test.sh <이름>                   # 재부팅 후 앱을 열지 않고 자동 시작·수신 확인(먼저 fgs로 한 번 동의)
bash situations.sh <이름>                            # 서비스 하나로 7개 상황 연속 확인
```

- 동결 여부: `adb shell dumpsys activity processes | grep -A3 com.hyundaiapp.freezeprobe` 의 `isFrozen`
